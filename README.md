# OnPair benchmark suite

Reproducible benchmark harness for **OnPair: Short String Compression for
Fast Random Access**. Every number, table, and figure in the paper is
produced by this repository: each measurement cell runs a baseline through
an identical subprocess protocol, verifies a byte-exact round-trip before
recording anything, and lands in an SQLite store from which the paper's
tables and figures are generated by scripts; there are no hand-entered
numbers.

## Requirements

- Linux on x86-64 (the point-access latency path uses `rdtscp`).
- GCC >= 13 (C++20), CMake >= 3.24, Python >= 3.11, `make`.
- ~25 GB disk for datasets, ~10 GB for build + result stores.
- Network access for dataset download and two pinned source fetches
  (the OnPair library and its Boost.Unordered dependency); all other
  baselines are vendored under `third_party/` with pinned provenance.

## Quick start (5 minutes, no datasets needed)

```sh
make smoke
```

Builds everything, creates the Python venv, runs the C++ and Python test
suites, and drives an end-to-end measurement of every baseline on a
committed synthetic fixture. Final line: `SMOKE OK`.

## Reproducing the paper

```sh
./reproduce.sh build        # deps + build + tests          (~10 min)
./reproduce.sh datasets     # download + materialise        (1-3 h, network)
./reproduce.sh headline     # main results table            (~40 h, see note)
./reproduce.sh access       # point-access latency table    (~3 h)
./reproduce.sh ablations    # threshold/capacity/seed/block/skew (~1 h)
./reproduce.sh modelsize    # RLZ reference-size sweep      (~15 min)
./reproduce.sh synthetic    # parametric synthetic sweep    (~30 min)
./reproduce.sh scale        # N-sweep vs Re-Pair            (~1 h)
./reproduce.sh paper        # regenerate tables/figures + claims audit (~1 min)
```

or `./reproduce.sh all`. Stages are independent once `build` and `datasets`
have run; `paper` consumes whichever result stores exist and skips the rest.

Note on the `headline` runtime: it is dominated by SentencePiece BPE
training, repeated for each of the 11 samples per cell (a single BPE-64K
training pass takes 35-60 minutes on the three largest columns). That cost
is not harness overhead; it is one of the paper's measured results. Every
other measurement stage combined takes about six hours, so a practical
order is: `ablations`/`access`/`scale` first, `headline` overnight.

### What maps to what

| Paper artifact | Producing stage | Result store (`build/`) |
|---|---|---|
| Main results table (ratio, C, D) | `headline` | `results.sqlite` |
| Point-access latency table + latency figure | `access` | `ra_headline_results.sqlite` |
| Pareto figure | `headline` | `results.sqlite` |
| Threshold/budget figure | `ablations` (A1, A3) | `a1/a3_results.sqlite` |
| Capacity sweep + model-size figure | `ablations` (A2, A4) + `modelsize` | `a2/a4_results.sqlite`, `rlz_sweep2_results.sqlite` |
| Block-size / query-skew results | `ablations` (A5, A6) | `a5/a6_results.sqlite` |
| Seed-sensitivity numbers | `ablations` (A7) | `a7_results.sqlite` |
| Synthetic-sweep figure | `synthetic` | `vd_results.sqlite` |
| Scalability (N-sweep) numbers | `scale` | `nsweep_results.sqlite` |

`./reproduce.sh paper` writes `build/figures/`, the LaTeX tables, and a
`claims_ledger.json` holding every headline number keyed by claim id. It
finishes with `tools/claims_audit.py`, which re-derives every quantitative
claim made in the paper's prose from the stores and prints PASS/FAIL per
claim — the same gate the submitted numbers passed.

## Portability notes

- **AVX-512 is not required.** The build uses `-march=native`; FSST's
  optional AVX-512 encoder path is compile-time gated and falls back to a
  scalar stub on CPUs without it (the paper's numbers were measured on an
  AVX2-only machine, with FSST's decoder scalar by design). Whether the
  AVX-512 path is active is recorded in the environment fingerprint, and it
  affects only FSST's compression throughput, no other metric.
- The point-access latency path requires x86-64 (`rdtscp`); on other
  architectures those cells return `refused-env` and the corresponding
  tests skip, everything else runs.

## Environment control

Throughput and latency stages refuse to run (`status=refused-env`) unless
the environment is controlled, because the paper's numbers were measured at
a fixed clock:

```sh
sudo cpupower frequency-set -g performance   # or per-CPU sysfs writes
echo 1 | sudo tee /sys/devices/system/cpu/intel_pstate/no_turbo
```

Pin measurements to one isolated core with `PIN_CPUS=<core>` (the drivers
do this themselves by default). Compression *ratios* are clock-independent
and reproduce bit-exactly on any machine; throughput scales with the clock
(the paper reports the fixed-clock numbers and quantifies the turbo delta
in its setup section).

## Datasets

`./reproduce.sh datasets` (= `make datasets`) downloads, SHA-verifies,
extracts, and splits every corpus per `experiments/datasets.yaml`:

| Column | Source |
|---|---|
| DBpedia abstracts | DBpedia short-abstracts 2022.12.01 dump (first 1M abstracts) |
| MS MARCO URLs / queries | MS MARCO ranking corpus |
| Amazon book titles | Amazon Reviews 2023 (McAuley Lab), Books metadata |
| TPC-H `p_name`, `c_comment` | generated locally via DuckDB's `tpch` extension, SF=10 |
| DBLP titles/authors | DBLP XML dump (non-headline; below the cardinality bar) |

Columns are kept **in their original dump order** — never sorted, shuffled,
or truncated (DBpedia's 1M-abstract cap is the only subsetting). Extraction
is deterministic; `datasets.yaml` records the SHA-256 of both the raw dumps
and the materialised columns, so a reviewer can verify byte-identical
inputs before measuring anything.

## Layout

| Path | Role |
|---|---|
| `runners/` | one C++ runner per baseline (NDJSON-over-stdio protocol) |
| `orchestrator/` | Python driver: cell scheduling, env probe, SQLite store |
| `experiments/` | grid definitions (YAML) + per-study drivers |
| `tools/` | dataset extractors, table/figure generators, claims audit |
| `schema/` | result-store DDL |
| `tests/` | C++ (ctest) + Python (pytest) suites |
| `third_party/` | vendored baselines, each with a PROVENANCE.txt (URL, SHA, licence) |
| `external/` | OnPair library FetchContent pin (commit SHA) |
| `docs/benchmark/` | architecture + per-baseline configuration/fairness notes |

## Fairness rules (uniform across baselines)

- Single-threaded everywhere; lint gates forbid thread APIs in runners.
- Training/construction time is inside the compress timed region for every
  baseline that trains (OnPair, BPE, FSST, RLZ, Re-Pair).
- Compression ratio counts payload only (dictionary + token stream / blocks
  / grammar) and excludes per-row offset metadata uniformly, since every
  scheme keeps the same kind of offset array.
- Every cell must pass a byte-exact round-trip and point-access correctness
  gate before its measurements are recorded.
- Per-baseline configuration rationale: `docs/benchmark/fairness/*.md`.
